# Агент на роутере (`agent/`)

## Почему ucode

На роутере только busybox, без python и jq. ucode уже стоит: на нём написан forkop. В ucode есть JSON, `fs` и запуск процессов, поэтому разбор clash API и отчёты пишутся нормально, без sed по JSON. HTTP через `curl` (он есть на роутерах пользователя).

## Файлы на роутере

```
/usr/bin/listok-agent            # ucode-скрипт (agent/listok-agent.uc)
/etc/init.d/listok-agent         # procd: один процесс на все секции (agent/listok-agent.init)
/etc/config/listok               # uci: server, server_ip, proxy, token агента, mode, interval, секции и токены фидов; права 600
/etc/listok/<section>.lst        # последний полученный фид (флеш: overlay, переживает ребут)
/etc/listok/<section>.etag
/tmp/listok/                     # временные файлы запросов
```

Команды: `listok-agent run` (цикл, его запускает procd), `sync <секция>` (одна загрузка без forkop, для установщика), `status`, `uninstall`, `version`.

## Настройки (`/etc/config/listok`, секция `agent`)

| Опция | Что |
|---|---|
| `server` | адрес listok (`LISTOK_BASE_URL`) |
| `server_ip` | необязательно: IP сервера в сети роутера, `curl --resolve` (D-028) |
| `proxy` | необязательно: `curl -x`, например служебный прокси forkop `http://127.0.0.1:4534` (запросы пойдут через VPN) |
| `token` | токен агента |
| `mode` | `wait` (по умолчанию) — держать одно соединение, изменения за секунды; `poll` — проверка раз в `interval` |
| `interval` | для `poll`: секунд между проверками, не меньше 60 (по умолчанию 300) |

Секции `feed`: `section` и `token` фида. После правки — `/etc/init.d/listok-agent reload`. Новая секция подхватывается переустановкой: её нужно ещё прописать в forkop, это делает установщик. Режим и интервал выбираются и при выдаче ссылки установки.

## Как агент ходит к серверу

`curl` с `--connect-timeout 10`, плюс `--resolve` при `server_ip` (D-028: роутер в одной сети с сервером, обращаясь к домену listok, получает собственный внешний IP и попадает в свой LuCI — проверено) и `-x` при `proxy`.

## Цикл синхронизации (один процесс на все секции, D-032)

1. `POST /agent/v1/wait` с версиями (ETag) всех секций: `{feeds: {main: "…", geo: "…"}, wait: 55}` (в режиме `poll` — `wait: 0`). Сервер отвечает, как только изменилась или пропала хоть одна секция, либо по таймауту: `{changed: [...], gone: [...]}`.
2. Изменившиеся секции скачиваются по `/f/<token>.lst` и проверяются: первой строкой `listok-sentinel.invalid`, остальные — домен, IPv4- или IPv6-подсеть. Отличается от файла — атомарно `mv` поверх `/etc/listok/<section>.lst`, etag сохраняется. На флеш пишем только при реальном изменении.
3. **Один** `forkop list_update` на все изменившиеся секции (forkop и так обновляет все разом), D-029:
   - если идёт чужое обновление (`/var/run/forkop_list_update.pid` с живым процессом) — ждать до 5 мин;
   - **код выхода не используется**: при чужом обновлении forkop пишет «уже идёт» и выходит с 0, а при недоступном внешнем списке (тот же discord.lst) — с 1, хотя наш локальный файл применился;
   - успех секции — `/tmp/sing-box/rulesets/<section>-lists-ruleset.json` пересобран после вызова и содержит сторожевую запись. Иначе ещё две попытки через 10 с.

   Применение занимает около 20 с: forkop проверяет доступ к GitHub и перекачивает все списки по ссылкам.
4. `POST /agent/v1/applied` по каждой секции.
5. Скачивание дало 404 — ссылку фида могли перевыпустить: агент спрашивает `hello`, записывает новый токен в `/etc/config/listok` и пробует снова. Секция «пропала» (`gone`: фид удалён или выключен) — `hello` и пауза 5 мин.
6. Сеть или 5xx → пауза 5 с, удваивается до 5 мин. 401 (агент отвязан на сервере) → пауза час. Файлы не трогаются.
7. В режиме `poll` после проверки — пауза `interval`, между проверками у агента нет дочерних процессов.
8. `hello` при старте и раз в час: версии агента, forkop и sing-box (из `opkg list-installed`), режим и интервал. Ответ — фиды с токенами: так подхватывается перевыпущенная ссылка. Фид секции, которой нет в локальном конфиге, — предупреждение в журнал.

Журнал: `logread -e listok-agent`.

## Нагрузка

Замер на NanoPi R3S (4×Cortex-A55), 2026-10-04:

| | агент 0.1.0 (процесс на секцию, 2 секции) | агент 0.2.0, `wait` | агент 0.2.0, `poll` |
|---|---|---|---|
| процессы в покое | 2 × ucode + 2 × curl | 1 × ucode + 1 × curl | 1 × ucode |
| память (PSS) | ~10 МБ | ~0,3 МБ + curl (~4,5 МБ с OpenSSL по HTTPS) | ~0,3 МБ |
| процессор в покое | ~1,4 % ядра (TLS-рукопожатие раз в минуту на секцию) | одно рукопожатие в минуту на роутер | только в момент проверки |
| задержка изменения | секунды + ~20 с forkop | секунды + ~20 с forkop | до `interval` + ~20 с forkop |

Основная статья расхода в покое — TLS: каждый запрос curl заново устанавливает соединение и разбирает хранилище сертификатов. На слабых роутерах (MIPS, 64–128 МБ) — режим `poll`.

## Проверка без изменений на роутере

`LISTOK_UCI_DIR`, `LISTOK_STATE_DIR`, `LISTOK_TMP_DIR` переносят конфиг и файлы (например, в `/tmp/lt`), `LISTOK_DRY_RUN=1` не вызывает forkop, `LISTOK_DEBUG=1` дублирует журнал в stderr. Так агент проверялся на домашнем роутере 2026-10-04 против локального listok через `ssh -R`: изменение доходило меньше чем за секунду, перевыпущенная ссылка подхватывалась сама через `hello`, режим `poll` с интервалом 60 с подхватил изменение на следующей проверке, обрыв связи — паузы 5 → 10 → 20 с. Синтаксис без запуска: `ucode -c -o /tmp/x.ucb listok-agent.uc`.

## Отчёты из clash API (этап 4, ещё не сделано)

- Раз в 30 с: `GET http://127.0.0.1:9090/connections` (с `Authorization: Bearer <secret>`, если задан `yacd_secret_key`).
- Берутся соединения, у которых в `chains` есть `direct-out`, а `metadata.host` не пустой и не IP. Копятся в памяти: host → hits, bytes, пример IP/порта/сети, rule.
- Раз в `report_interval_s` (по умолчанию 300) уходит на `/agent/v1/report`, накопленное очищается.
- Локальный фильтр не отправляет домены LAN и `*.lan`/`*.local`, а также то, что уже есть в собственных фидах.
- Выключается через `report_enabled` (на сервере для роутера и в uci локально). Для роутеров других пользователей по умолчанию **выключено**.

На сервере отчёты попадают в `observations`. Они проходят через `suggestion_ignores` и проверку покрытия. В интерфейсе показываются хосты со статусом `new`, сгруппированные по eTLD+1: «добавить в список…», «скрыть», «игнорировать шаблон».

## Установка

Карточка роутера → «Агент на роутере» → «Выдать ссылку установки»: режим (мгновенно или раз в N минут) и, если роутер в одной сети с сервером, IP сервера в этой сети. Появляется команда, её выполняют на роутере под root:

```
curl -fsSL [--resolve listok.example.com:443:<IP>] 'https://listok.example.com/install/<token>[?ip=<IP>&mode=poll&interval=<сек>]' | sh
```

Ссылка одноразовая, живёт 24 ч, в БД хранится только её хеш. **Тратится только запросом от curl или wget** (D-030): браузер и предпросмотр ссылки в мессенджере получают страницу-подсказку. Без включённых фидов ссылка не тратится, установщик объясняет почему.

Установщик (`agent/install.sh.tmpl`, токены подставляет сервер):
1. Проверяет root, forkop, ucode, curl и что все секции фидов есть в forkop.
2. Бэкап `/etc/config/forkop.bak-listok-<дата>`.
3. Кладёт агент, init-скрипт и `/etc/config/listok` (с `umask 077`).
4. Первая загрузка каждого фида (`listok-agent sync`), чтобы `/etc/listok/*.lst` существовали.
5. В forkop: из `domain_ip_lists` секции убираются ссылки на фиды этого сервера (`<server>/f/…`, если их вставляли вручную), добавляется `/etc/listok/<section>.lst`. Если стало иначе, чем было, — `uci commit forkop`, `/etc/init.d/forkop reload`: **единственный перезапуск forkop**. При переустановке с теми же секциями forkop не трогается.
6. `listok-agent` enable + restart.

Удаление: `listok-agent uninstall` убирает пути `/etc/listok/…` из forkop (forkop перезапустится), останавливает и выключает службу, удаляет файлы. На сервере «Отвязать агент» забывает токен агента (фиды продолжают отдаваться).

Самообновление (этап 5, ещё не сделано): `hello` уже возвращает актуальную версию, карточка роутера показывает «есть новая». Агент будет скачивать `/agent/listok-agent.uc`, проверять sha256 и перезапускаться.
