# Агент на роутере (`agent/`)

## Почему ucode

На роутере только busybox, без python и jq. ucode уже стоит: на нём написан forkop. В ucode есть JSON, `fs` и запуск процессов, поэтому разбор clash API и отчёты пишутся нормально, без sed по JSON. HTTP через `curl` (он есть на роутерах пользователя).

## Файлы на роутере

```
/usr/bin/listok-agent            # ucode-скрипт (agent/listok-agent.uc)
/etc/init.d/listok-agent         # procd: один процесс на все секции (agent/listok-agent.init)
/etc/config/listok               # uci: server, server_ip, proxy, token агента, mode, interval, секции и токены фидов; права 600
/etc/listok/<section>.lst        # последний полученный фид (флеш: overlay, переживает ребут)
/etc/listok/<section>.etag
/tmp/listok/                     # временные файлы запросов
```

Команды: `listok-agent run` (цикл, его запускает procd), `sync <секция>` (одна загрузка без forkop, для установщика), `check <секции…>` (есть ли секции в forkop), `attach <секции…>` (подключить файлы к секциям forkop), `status`, `uninstall`, `version`.

Секций у агента может не быть: с 0.4.0 он ставится до их подключения, сообщает серверу секции forkop и подключает новые сам, когда их отмечают в интерфейсе (D-038).

Агент работает с forkop 1.x и 2.x (D-036). Ветку определяет `forkop.settings.config_version`. Секция forkop ищется по названию из LuCI (`option label`, в forkop 2 секции анонимные), потом по имени UCI.

## Настройки (`/etc/config/listok`, секция `agent`)

| Опция | Что |
|---|---|
| `server` | адрес listok (`LISTOK_BASE_URL`) |
| `server_ip` | необязательно: IP сервера в сети роутера, `curl --resolve` (D-028) |
| `proxy` | необязательно: `curl -x`, например служебный прокси forkop `http://127.0.0.1:4534` (запросы пойдут через VPN) |
| `token` | токен агента |
| `mode` | `wait` (по умолчанию) — держать одно соединение, изменения за секунды; `poll` — проверка раз в `interval` |
| `interval` | для `poll`: секунд между проверками, не меньше 60 (по умолчанию 300) |

Секции `feed`: `section` и `token` фида. После правки — `/etc/init.d/listok-agent reload`. Новая секция подхватывается переустановкой: её нужно ещё прописать в forkop, это делает установщик. Режим и интервал выбираются и при выдаче ссылки установки.

## Как агент ходит к серверу

`curl` с `--connect-timeout 10`, плюс `--resolve` при `server_ip` (D-028: роутер в одной сети с сервером, обращаясь к домену listok, получает собственный внешний IP и попадает в свой LuCI — проверено) и `-x` при `proxy`.

**Один корень вместо всего хранилища (D-034).** При старте агент через `openssl s_client -showcerts` берёт цепочку сервера и ищет первый сертификат, чей издатель есть в `/etc/ssl/certs/<issuer_hash>.N`, затем проверяет запросом `/healthz`, что с этим корнем всё проходит, и дальше передаёт curl `--cacert <этот файл>`. Нет `openssl`, корня или проверка не прошла — полное хранилище. Ошибка связи при закреплённом корне — корень ищется заново (сертификат могли перевыпустить другим корнем).

## Цикл синхронизации (один процесс на все секции, D-032)

1. `POST /agent/v1/wait` с версиями (ETag) всех секций: `{feeds: {main: "…", geo: "…"}, wait: 55, added: true}` (в режиме `poll` — `wait: 0`). Сервер отвечает, как только изменилась, пропала или появилась хоть одна секция, либо по таймауту: `{changed: [...], gone: [...], added: [...]}`.
2. Изменившиеся секции скачиваются по `/f/<token>.lst` и проверяются: первой строкой `listok-sentinel.invalid`, остальные — домен, IPv4- или IPv6-подсеть. Отличается от файла — атомарно `mv` поверх `/etc/listok/<section>.lst`, etag сохраняется. На флеш пишем только при реальном изменении.
3. Применение. **forkop 2.x:** ядро само перечитывает файл, как только он сменился, а подсети в nft переносит служба forkop. Агент перед записью запоминает `revision` rule set каждой секции (`GET /providers/rules/<tag>` в clash API, тег — из конфига sing-box по пути файла) и после записи ждёт до 15 с, пока ревизия сменится. Сменилась — `ok`; rule set с этим путём нет в конфиге — «forkop не подключил файл»; ревизия не сменилась — «ядро не перечитало файл» (ошибка в журнале sing-box). Задержка — доли секунды.

   **forkop 1.x:** **один** `forkop list_update` на все изменившиеся секции (forkop и так обновляет все разом), D-029:
   - если идёт чужое обновление (`/var/run/forkop_list_update.pid` с живым процессом) — ждать до 5 мин;
   - **код выхода не используется**: при чужом обновлении forkop пишет «уже идёт» и выходит с 0, а при недоступном внешнем списке (тот же discord.lst) — с 1, хотя наш локальный файл применился;
   - успех секции — `/tmp/sing-box/rulesets/<section>-lists-ruleset.json` пересобран после вызова и содержит сторожевую запись. Иначе ещё две попытки через 10 с.

   Применение занимает около 20 с: forkop проверяет доступ к GitHub и перекачивает все списки по ссылкам.
4. `POST /agent/v1/applied` по каждой секции.
5. Скачивание дало 404 — ссылку фида могли перевыпустить: агент спрашивает `hello`, записывает новый токен в `/etc/config/listok` и пробует снова.
   - **`added`** — секцию подключили в интерфейсе: `hello` (токен её фида), скачать и проверить фид, записать секцию в `/etc/config/listok`, подключить файл к forkop (как `attach`: один `/etc/init.d/forkop reload`), доложить `applied`. Секции нет в forkop — `applied` с ошибкой «в forkop нет секции» и пауза 10 мин; фид не скачался — повтор через минуту. Пока есть такая пауза, `wait` идёт без `added`, чтобы сервер не отвечал сразу раз за разом. Секции, подключённые, пока агент был выключен, подхватываются так же после `hello` при старте и раз в час.
   - **`gone`** — секцию отключили (или выключили): в её файле остаётся только сторожевая запись — записи listok уходят с роутера сразу, без перезапуска; секция убирается из `/etc/config/listok`, путь в forkop остаётся (повторное подключение без перезапуска).
6. Сеть или 5xx → пауза 5 с, удваивается до 5 мин. 401 (агент отвязан на сервере) → пауза час. Файлы не трогаются.
7. В режиме `poll` после проверки — пауза `interval`, между проверками у агента нет дочерних процессов.
8. После первого успешного `hello` агент докладывает `applied` по всем секциям: файл есть и forkop его подхватил — `ok`, иначе ошибка «forkop не подхватил файл». forkop 1.x: в rule-set секции есть сторожевая запись; forkop 2.x: rule set с путём файла есть в конфиге sing-box и ядро отвечает по нему в clash API (сразу после установки ядро ждём до 30 с). Так статус виден сразу после установки или перезагрузки роутера.
9. `hello` при старте и раз в час: версии агента, forkop и sing-box (из `opkg list-installed`; версия forkop при её отсутствии — `config_version`), режим, интервал и секции forkop (`forkop_sections`: название — `label`, в 1.x имя секции; UCI-имя; `action`). Ответ — фиды с токенами: так подхватывается перевыпущенная ссылка, а фид секции, которой нет в локальном конфиге, подключается (п. 5, `added`).

Журнал: `logread -e listok-agent`.

## Нагрузка

Замер на NanoPi R3S (4×Cortex-A55), 2026-10-04:

| | 0.1.0 (процесс на секцию, 2 секции) | 0.2.0, `wait` | 0.2.1, `wait` (один корень) | 0.2.x, `poll` |
|---|---|---|---|---|
| процессы в покое | 2 × ucode + 2 × curl | 1 × ucode + 1 × curl | 1 × ucode + 1 × curl | 1 × ucode |
| память (PSS) | ~9,6 МБ | ~6,6 МБ (агент 0,4 + curl 6,2) | так же | ~0,4 МБ |
| процессор в покое | ~1,4 % ядра | ~0,9 % ядра | ~0,25 % ядра (расчёт: запрос curl 7,5 тика вместо 30) | только в момент проверки |
| задержка изменения | секунды + ~20 с forkop | секунды + ~20 с forkop | секунды + ~20 с forkop (forkop 2: ~1 с) | до `interval` + ~20 с forkop (forkop 2: + ~1 с) |

Почти весь расход в покое — curl: каждый запуск заново устанавливает TLS-соединение, а с полным хранилищем ещё и разбирает ~150 корней (224 КБ) — ~0,3 с процессора Cortex-A55 на запрос. С одним корнем — ~0,08 с. На слабых роутерах (MIPS, 64–128 МБ) — режим `poll`.

## Проверка без изменений на роутере

`LISTOK_UCI_DIR`, `LISTOK_STATE_DIR`, `LISTOK_TMP_DIR` переносят конфиги (`listok` и `forkop`) и файлы (например, в `/tmp/lt`), `LISTOK_DRY_RUN=1` не вызывает forkop, `LISTOK_DEBUG=1` дублирует журнал в stderr. Так агент проверялся на домашнем роутере 2026-10-04 против локального listok через `ssh -R`: изменение доходило меньше чем за секунду, перевыпущенная ссылка подхватывалась сама через `hello`, режим `poll` с интервалом 60 с подхватил изменение на следующей проверке, обрыв связи — паузы 5 → 10 → 20 с. Синтаксис без запуска: `ucode -c -o /tmp/x.ucb listok-agent.uc`.

Агент 0.4.0 (2026-10-31) проверен там же: без секций работает; `forkop_sections` отдаёт название, UCI-имя и тип; `add_sections` скачивает фид с поддельного сервера (uhttpd), пишет секцию в конфиг и подключает файл к forkop, секцию, которой нет в forkop, и секцию без фида откладывает; `drop_sections` оставляет в файле только сторожевую запись, убирает секцию из конфига агента, путь в forkop не трогает.

Поддержка forkop 2 (агент 0.3.0) проверена 2026-10-31 в контейнере `openwrt/rootfs:x86_64-24.10.4` на поддельном конфиге forkop 2 и поддельном clash API (статические ответы uhttpd): `check` находит анонимную секцию по `label` и именованную по имени, `attach` ставит путь в `rule_set_with_subnets` (у DNS-секции в `rule_set`), убирает ссылку на фид и не трогает чужие наборы, повтор ничего не меняет; ветка 1.x пишет в `domain_ip_lists`; применение ждёт смены ревизии и сообщает об ошибке, если её нет или rule set не подключён; `uninstall` убирает пути из всех трёх опций. Первый запуск на живом forkop 2 (2026-10-31, агент 0.3.0): установка прошла, секции нашлись, но применение упало с `access to undeclared variable apply_core` — `apply()` вызывала функцию, объявленную ниже по файлу, а тест в контейнере звал `apply_core()` напрямую. В 0.3.1 порядок исправлен, контейнерный тест идёт через `apply()`, а `TestNoForwardCalls` в `agent_test.go` ловит такие вызовы без ucode. Агент 0.3.1 на том же роутере: от «новые версии фидов» до «применено» ~1 с, три правки подряд, дубль пути в `rule_set` и `rule_set_with_subnets` убран переустановкой.

## Отчёты из clash API (этап 4, ещё не сделано)

- Раз в 30 с: `GET http://127.0.0.1:9090/connections` (с `Authorization: Bearer <secret>`, если задан `yacd_secret_key`).
- Берутся соединения, у которых в `chains` есть `direct-out`, а `metadata.host` не пустой и не IP. Копятся в памяти: host → hits, bytes, пример IP/порта/сети, rule.
- Раз в `report_interval_s` (по умолчанию 300) уходит на `/agent/v1/report`, накопленное очищается.
- Локальный фильтр не отправляет домены LAN и `*.lan`/`*.local`, а также то, что уже есть в собственных фидах.
- Выключается через `report_enabled` (на сервере для роутера и в uci локально). Для роутеров других пользователей по умолчанию **выключено**.

На сервере отчёты попадают в `observations`. Они проходят через `suggestion_ignores` и проверку покрытия. В интерфейсе показываются хосты со статусом `new`, сгруппированные по eTLD+1: «добавить в список…», «скрыть», «игнорировать шаблон».

## Установка

Страница роутера → блок «Агент» (без агента — «Подключение за два шага»): готовая команда видна сразу; режим (мгновенно или экономно, раз в N минут) и, если роутер в одной сети с сервером, IP сервера в этой сети подставляются в неё на лету. Команду выполняют на роутере под root:

```
curl -fsSL [--resolve listok.example.com:443:<IP>] 'https://listok.example.com/install/<token>[?ip=<IP>&mode=poll&interval=<сек>]' | sh
```

Ссылка одноразовая, живёт 24 ч. В БД — её хеш (для поиска) и сам токен, чтобы страница показывала команду повторно (D-039); оба стираются при установке. **Тратится только запросом от curl или wget** (D-030): браузер и предпросмотр ссылки в мессенджере получают страницу-подсказку. Секций у роутера может ещё не быть: агент ставится и без них.

Установщик (`agent/install.sh.tmpl`, токены подставляет сервер):
1. Проверяет root, forkop, ucode, curl. Кладёт агент во `/tmp/listok/` и вызывает `check`: все секции фидов есть в forkop (по названию из LuCI или имени). До этого на роутере ничего не меняется. Секций может не быть — тогда шаги 4–5 пропускаются, forkop не трогается.
2. Бэкап `/etc/config/forkop.bak-listok-<дата>`.
3. Переносит агент в `/usr/bin`, кладёт init-скрипт и `/etc/config/listok` (с `umask 077`).
4. Первая загрузка каждого фида (`listok-agent sync`), чтобы `/etc/listok/*.lst` существовали: forkop 2 не принимает пустой или отсутствующий файл.
5. `listok-agent attach`: в опции списков секции (forkop 1 — `domain_ip_lists`, forkop 2 — `rule_set_with_subnets`, у DNS-секции `rule_set`) убираются ссылки на фиды этого сервера (`<server>/f/…`, если их вставляли вручную), добавляется `/etc/listok/<section>.lst`. Из остальных опций секции этот путь убирается: в LuCI forkop 2 набор лежит либо в `rule_set` (без подсетей), либо в `rule_set_with_subnets`, и путь, добавленный руками без флажка, иначе оказался бы в обеих. Если стало иначе, чем было, — `uci commit forkop`, `/etc/init.d/forkop reload`: **единственный перезапуск forkop**. При переустановке с теми же секциями forkop не трогается.
6. `listok-agent` enable + restart.

Удаление: `listok-agent uninstall` убирает пути `/etc/listok/…` из forkop (из всех трёх опций; forkop перезапустится), останавливает и выключает службу, удаляет файлы. На сервере «Отвязать агент» забывает токен агента (фиды продолжают отдаваться).

Самообновление (этап 5, ещё не сделано): `hello` уже возвращает актуальную версию, карточка роутера показывает «есть новая». Агент будет скачивать `/agent/listok-agent.uc`, проверять sha256 и перезапускаться.
